## 一、开发手册设计是否合理

**结论：大方向合理，用户自用的 MVP 来说过度设计了；文档本身已经和代码明显不一致，需要重新整理。**

### 1.1 合理的地方

- **边界划分清楚**：web / api / contracts / database / learning-domain / learning-agent / ai-access 七层职责明确，代码也按这个落地了，`check-boundaries` 脚本会强制检查依赖方向。
- **对安全和失败的态度对**：配置有问题就拒绝启动；mock 和 live 数据分开放；模型输出必须校验通过才写入；题目答案在作答前不下发；用 HttpOnly + SameSite=strict 的 Cookie 加 CSRF 和 Origin 校验；有幂等回执，任务执行有 runId/attemptId 防重。这些都是认真想过的。
- **把"自动生成的内容"当成要用户确认的候选**：知识点先由用户确认，再进入复习，和产品目标对得上。
- **README 写得诚实**：会话存在内存里、轮换 SESSION_SECRET 会导致凭证失效等限制都写明了。

### 1.2 问题

1. **篇幅太长，几类内容混在一起。** 19 章里同时有规格、当前进度和设计理由，还反复出现"不代表……""不能……"这类保留说明。读的人很难快速判断现在到底实现了什么。
2. **文档已经和代码对不上。** 见下表。
3. **复杂度和场景不匹配。** 单用户自用，却设计了租约、多 worker、多重鉴权等机制。
4. **关键数字没定。** 数据量预期、保留多久、输入上限这些关键数字都没写死。结果就是下文 H2 那种上传上限和模型输入上限互相冲突的问题。
5. **没有记录"为什么当初这么选"。** 比如为什么用单行 JSONB、为什么不用工具调用，这类决定都没有成文。

#### 手册与代码不一致的地方

| 手册里的说法 | 实际情况 |
|---|---|
| §4.1 说 `design/sanxing-design-handoff/` "目前不存在" | 这个目录已经存在 |
| §5.1 / §5.3 说依赖还"不是已安装的"、目录"不代表已创建" | 依赖已装好，目录也已建好 |
| §5.3 规划了 `docs/decisions/`、`docs/evaluations/` | 两个目录都没有 |
| §4.3 检查清单里还有"模型费用上限" | §1.3 说不设预算，前后矛盾 |
| §16.2 列了 `STORAGE_DRIVER`、`OBJECT_STORAGE_*`、`MODEL_BASE_URL`、`AI_CLEANUP_TIMEOUT_MS` | 都没有实现；设置 `MODEL_BASE_URL` 反而会让启动被拒绝 |
| §6.2 / §8.2 描述了 streamFn、工具白名单和 `propose_*` 工具 | 实际是不带工具、一次请求拿一个结构化结果 |
| §10.3 定义了 SSE 事件 `assistant_text_delta`、`question_ready` 等 | 实际 SSE 只推送任务状态，前端用的也是每秒轮询 |
| §9.1 规划了按实体拆分的表 | 实际是一行 JSONB 存全部数据 |
| §9.5 要求知识点有内容版本，证据引用旧版本 | 实际直接覆盖原内容，不保留历史（见 M1） |

### 1.3 建议

- 把手册拆成两份：
  - **《产品与架构规格》**：相对稳定的部分；
  - **《实现状态与偏差表》**：每次迭代更新，列出"规划 / 已实现 / 有意偏离及原因"。
- 删掉或标注已经过时的段落；第 6、8、10 章按当前实现重写，原来的方案移到"未来演进"。
- 给每个关键常量（上传上限、输入上限、复述字数、追问次数）设一个唯一出处，写进 contracts 包，文档和代码都引用它。

## 二、项目存在的问题（按严重程度排序）

### 高优先级（会让功能直接失败或损失明显）

#### H1. 提取知识点的提示词和校验规则矛盾，live 模式下整个提取任务可能失败

- **位置**：`packages/learning-agent/prompts/extract.md:1`、`packages/learning-domain/src/service.ts:393`
- **现象**：提示词告诉模型"无直接资料依据则 sourceIds=[]"，但 `finishRun` 要求每个候选的 `sourceIds.length > 0`，否则报 `INVALID_REFERENCE`。
- **影响**：只要模型按提示词返回一个没有引用来源的候选，整次提取就判为失败，这次请求的钱也白花了。
- **修复**：二选一。要么改提示词要求必须引用资料；要么校验允许空数组，在界面上标成"无资料依据"。

#### H2. 模型输入上限 48K 和上传、复述的上限不一致

- **位置**：`packages/learning-domain/src/service.ts:61`
- **现象**：`JSON.stringify(task).length > 48_000` 时拒绝提交。但上传每个文件默认允许 131072 字节、最多 5 个，复述每个字段允许 20000 字。用户能正常上传、正常保存，到提交时才报"输入过长"。
- **附带问题**：每次追问、出题都会把全部资料原文重新发一遍，和手册 §6.3"只发送相关片段"不符，费用会成倍增长。
- **修复**：在 contracts 里统一预算，上传时就提示还剩多少输入额度；追问和出题只带相关片段或摘要。

#### H3. 整个应用数据存在一行 JSONB 里，再加上多处高频轮询，用得越久越卡

- **位置**：`packages/database/src/index.ts`、`packages/learning-domain/src/worker.ts:20`、`apps/api/src/app.ts:104`、`apps/api/src/app.ts:161`、`apps/web/src/components/store.tsx`
- **现象**：
  - 每次读写都整行 SELECT、完整 zod 校验、递归检查、structuredClone，再整行 UPDATE，所有操作串行排队。
  - 文档原文和 `originalBase64` 也存在这一行里；幂等回执（receipts）从不清理。
- **全量读取的来源**：
  - 后台任务处理器每 500ms 全量读一次；
  - 每条 SSE 连接每秒全量读一次；
  - 每次写操作之后全量扫描一遍已取消的任务；
  - 前端每 1 秒自动保存一次，每次都写库、生成回执、重新拉全量状态。
- **影响**：现在 `data/live` 和 `data/mock` 已经各有 39M。每天用的话几个月内会明显变慢，CPU 也会一直被占着。
- **修复**（按投入从小到大）：
  1. 回执设过期时间并定期清理；
  2. 文档原文移出这一行，单独存表或存文件；
  3. 后台任务处理器改成有新任务时再唤醒，不再每 500ms 轮询；
  4. 中期按手册 §9.1 拆表。

#### H4. 登录限流实际上是全局一个计数，任何人都能把本人锁在外面

- **位置**：`apps/api/src/app.ts:17`、`apps/api/src/app.ts:57-63`
- **现象**：API 设了 `trustProxy: false`，而所有请求都经过 Next 转发，来源 IP 都是 127.0.0.1。按 `request.ip` 计数，相当于所有人共用一个计数器。
- **影响**：前端开发服务器监听 `0.0.0.0:3010`，局域网里任何人输错 8 次密码，你就会被锁 15 分钟。
- **修复**：让前端只监听 127.0.0.1；或者由 Next 传真实客户端 IP（例如 X-Forwarded-For），API 只信任本机代理发来的这个头。

#### H5. 拿不到用量数据时，已付费的有效结果会被丢掉

- **位置**：`packages/learning-agent/src/index.ts:220`
- **现象**：`if (!observedUsage) fail('UNKNOWN_USAGE')`。只要模型服务没返回用量或返回 0，即使输出完全有效也会被丢弃，钱照样花了。
- **说明**：手册的设计是"记录为未知"，代码比手册更严。
- **修复**：保留结果，把用量标记为 unknown。

### 中优先级（逻辑缺陷，和设计不符）

#### M1. 复用已有知识点时直接覆盖原内容，没有历史版本

- **位置**：`packages/learning-domain/src/service.ts:163-164`、`service.ts:316`
- **现象**：直接改 title 和 description，`version++` 只是个计数。证据只记录了知识点 id，没有记录对应的内容版本，违反手册 §9.5。`saveUnderstanding` 和内容修改共用同一个版本号，无法区分是哪种修改。
- **修复**：给知识点内容建版本表或快照；证据同时记录 `knowledgeId` 和内容版本。

#### M2. `endSession` 收到的 `reason` 参数被忽略

- **位置**：`packages/learning-domain/src/service.ts:205-210`、`service.ts:257`
- **现象**：解析了 reason，最后却按有没有测验来写结束原因。更糟的是，有测验时 `finalizeQuiz` 已经把结束原因设为 `'assessed'`，紧接着又被覆盖成 `'user_ended'`。
- **修复**：使用传入的 reason；已经是 `assessed` 时不再覆盖。

#### M3. live 模式默认无法产生复习卡

- **现象**：live 下 `REVIEW_SCHEDULING_ENABLED` 默认为 false，`finalizeQuiz` 不会生成复习卡，所以复习流程在 live 下默认用不了。
- **说明**：这点有文档说明，但对用户来说属于"主流程断了"。
- **修复**：至少要在界面上明确提示；或者在确定默认策略后打开。

#### M4. 复习时写的回忆内容没有被使用

- **位置**：`reviewRecall`；`packages/learning-domain/src/service.ts:284`
- **现象**：`reviewRecall` 接受空回忆。复习测验只根据知识点描述生成，用户写的回忆完全不参与评估，这一步形同虚设。
- **修复**：要求回忆内容非空，并把它作为出题或评估的输入。

#### M5. 切换范围后，追问还会带上旧范围的内容

- **现象**：changeScope 之后，追问任务仍保留旧范围的对话轮次，可能还会带上已经从草稿里移除的资料。
- **修复**：切换范围后按新范围过滤对话轮次和资料。

### 低优先级（代码质量和细节）

| 编号 | 问题 | 位置 / 说明 |
|---|---|---|
| L1 | 测验状态更新没有递增版本号 | `service.ts:237-238` 把状态改成 `QUIZZING` 时没有 `version++`，乐观锁对这个状态变化不起作用 |
| L2 | 请求指纹的排序依赖系统语言环境 | fingerprint 排序用的是 `localeCompare`，换个环境指纹可能不同，导致幂等判断出错；应改成直接比较码点 |
| L3 | `/api/me` 白算一遍全量数据 | 只是为了取 capabilities，却计算了完整的状态投影 |
| L4 | 文档上传的幂等 key 在入口没有校验格式 | `/api/documents` 只校验了是字符串，格式到领域层才检查；应在入口统一校验 |
| L5 | `/state` 每次都返回全部内容 | 所有复述、文档全文和证据每次都下发，前端每个操作之后又全量重新拉取 |
| L6 | live 环境检查太严 | `assertLiveEnvironment` 只要发现任何 `OPENAI_*`、`ANTHROPIC_*` 或代理相关的环境变量就拒绝启动；对开发者机器不友好，至少应在报错里指出是哪个变量 |
| L7 | SSE 接口实际上没被使用 | SSE 只推送任务状态；前端没有用 EventSource，仍然在轮询（手册里却当成主要通道来写） |
| L8 | 项目不是 git 仓库 | 没有版本控制，建议马上 `git init`；根目录还有 `sanxing-design-handoff.zip` 和 `test-results/` 这类产物 |
| L9 | `data/live` 下有 `postmaster.pid` 和 `.sanxing.lock` | 可能是还在运行的实例，也可能是上次异常退出留下的；需确认下次启动时锁检测能正确处理这种残留 |

## 三、建议的处理顺序

1. **H1、H5、M2**：改动小、收益大，各自几行代码就能修。
2. **H4**：前端改成监听本机 + 传递真实 IP。
3. **H2**：在 contracts 里统一输入上限，追问和出题只发相关片段。
4. **H3**：先清理回执、把文档原文移出那一行、去掉 500ms 轮询，再考虑拆表。
5. **M1、M3、M4**：补上知识点版本、复习卡和回忆评估，让核心学习闭环在 live 模式下也能完整跑通。
6. 按第一部分的建议把手册拆成"规格"和"实现状态与偏差表"两份，同时 `git init`。

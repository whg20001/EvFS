## 2. 产品目标与核心原则

### 2.1 产品定位

打造以主动回忆为核心的学习教练，而不是仅有聊天入口的笔记管理器。

完整闭环：

```text
复述所学 → 澄清范围 → 确认知识点 → 追问与补全
        → 独立考核 → 留下证据 → 安排复习 → 再次检验
```

编辑器遵循设计包的三段输入：

1. 一省：今天学了什么。
2. 二省：哪里还说不清。
3. 三省：明天怎么用上。

长期产品还要帮助用户回答：以前学过的内容，现在是否仍能独立回忆和应用？

### 2.2 核心原则

1. **先回忆，后辅助**：鼓励先独立复述，再查看笔记；允许辅助，但必须记录辅助情况。
2. **以知识点为单位**：一篇笔记可以拆成多个知识点和回忆目标，不对整篇文章只给一个笼统分数。
3. **评价必须有证据**：用户自称学过、点击“我已经掌握”或接受 AI 补全，都不等于验证掌握。
4. **缺失不等于不会**：未提及的内容属于覆盖情况，不直接属于掌握状态。
5. **资料可追溯**：问题、冲突判断和评分依据尽量关联到具体来源版本和片段。
6. **AI 建议，代码执行**：AI 负责理解、生成和评价建议；代码负责权限、校验、状态流转、事务和排期。
7. **过程可中断**：用户可以离开、跳过或结束，不通过无限追问强迫完成流程。
8. **界面不伪造精度**：没有可靠依据的完整度、掌握度和保持率显示“待评估”或“暂无估计”。

### 2.3 示例

用户复述：“今天学了 Redis 缓存。”

正确行为：先确认学习范围是缓存使用、一致性还是内部数据结构，再依据回答与笔记追问。

错误行为：直接生成覆盖全部 Redis 知识的考卷，或把用户未提及的知识判定为“不会”。

### 2.4 效果指标

优先关注延迟后的独立回忆表现、重复误解减少情况和用户能否坚持完成合理负荷的复习。聊天轮数、签到天数和学习时长只能作为辅助指标，不能代替学习效果。

## 3. 范围与版本规划

### 3.1 MVP：验证闭环

已确认先供本人使用；建议选择一个熟悉的学习领域作为首批评估样例，不限制未来只能学习该领域。

- 三段文本复述、草稿保存、主题标签。
- 粘贴笔记与 TXT / Markdown 上传，包括格式限制、失败重试、移除和原文定位；不是只画一个上传按钮。
- AI 提取候选知识点、匹配已有知识点、引用来源、有限轮次追问。
- 用户确认、修订和拒绝 AI 建议，追问中可明确纳入补充资料。
- 单选题、简答题、答案暂存、正式提交、评分依据和结果页。
- 学习记录持久化、到期复习和可恢复的学习 / 复习会话。
- 简单知识点列表、详情、历史复述入口和真实学习时间线。
- 单用户受保护访问、显式 Provider 配置、费用记录与运行限制。

MVP 对应第 17 章的 P0、P1、P2；TXT / Markdown 基础上传在 P1 完成，不推迟到 P3。数据管理首版至少提供有说明、可验证的备份恢复、导出和删除操作路径，可先使用受控脚本，不必先做完整管理页面。

MVP 不承诺设计包中的全部附件格式和完整统计图表。未实现的入口应隐藏或清楚标注，不能展示可点击但无效的功能。

### 3.2 第二阶段：资料与可靠性

以下为候选扩展，待首版使用反馈后再决定，不是首期交付承诺：

- 文本型 PDF、DOCX 解析、页码选择及来源定位。
- 更丰富的题目变式、重复题控制和自动评分申诉流程。
- 周 / 月复习视图、学习统计和估计曲线。
- 数据导出、删除、成本监控与备份恢复的界面化。
- 根据实际负荷扩展后台任务队列；基础超时、重试、租约和恢复不能延期到此阶段。

### 3.3 第三阶段：个性化

- 扫描 PDF、图片 OCR、公式识别和语音转写。
- AI 周报、提醒与长期薄弱点分析。
- 基于足够复习数据的调度参数优化。
- 更丰富的应用题和跨主题分析。

### 3.4 暂不优先

多 Agent 协作、复杂知识图谱、向量数据库、微服务、原生移动 App、公开多人服务、社交排名和大量游戏化功能。只有出现明确需求和瓶颈时再引入。网页小屏适配仍在首版范围内。

### 4.2 需要显式处理的差异

首期资料格式按第 1.3 节的已确认决定执行；其余为本手册采用的建议修订方向，题量、指标和具体交互仍按第 4.3 节确认，不把设计示意当成事实：

| 交接包内容 | 风险或问题 | 建议方案 |
|---|---|---|
| 示例追问 5 题、测验 8 题 | 不是已确认的固定题量 | 做成配置；建议先试追问不超过 5 轮、测验 3–5 题 |
| 直接回答时默认采纳未确认知识点 | 容易把候选内容当作用户确认事实 | 保留未确认状态；进入考核前明确确认范围或标记范围不足 |
| “我已经掌握”直接标为已掌握 | 自我评价不等于作答证据 | 记录为用户自评，另行测试验证 |
| 根据“标准知识点”计算完整度 | 标准知识点来源未确定 | 无经确认的课程参考范围时不显示客观完整度百分比 |
| 混合测验、追问和预计保持率得到掌握度 | 指标含义不同，权重未验证 | 先分开展示证据；总指标需明确公式及版本 |
| 曲线复习后跳回 100% | 设计示意不是测量事实 | 显示为模型估计，不宣称每次答题后真实保持率为 100% |
| 固定第 1、2、4、7、15、30 天复习 | 不适合所有用户和知识点 | 建议真实排期采用 FSRS；固定节点仅用于明确标识的演示 |
| 正确后立刻标记误解已纠正 | 单次表现可能受提示影响 | 区分本次回答改正和延迟复习验证 |
| 支持全部文件格式、OCR、语音 | 超出已确认首期范围 | 首期只开放 TXT / Markdown 和粘贴笔记，其余入口隐藏 |
| 选择即提交、不能跳答 | 容易与草稿、主动跳过混淆 | 单选正式选择即提交；按顺序答题，允许明确跳过当前题，不允许跳到未来题查看 |
| 小屏知识库入口位于复盘页 | 延期复盘页会导致入口丢失 | MVP 导航独立保留知识库入口 |
| 追问中可附加资料和接受补全 | 不可变提交快照不能直接被覆盖 | 通过新的会话范围版本纳入，旧问题和旧题集仍引用原版本 |
| 每日一份复述，提交后仍可编辑 | 容易改变旧考核依据 | 每日草稿可编辑，提交生成不可变快照，修订形成新版本 |

`tokens.json` 的备注引用 `specs/review.md`，但交接包实际文件为 `specs/04-review.md`；实现时不要依赖不存在的路径。

## 5. 技术架构与目录规划

### 5.1 建议技术栈

| 层次 | 建议 | 原因 |
|---|---|---|
| 网页 | Next.js + React + TypeScript | 页面、路由和组件开发 |
| 服务端 | Node.js + Fastify + TypeScript | 长运行 Agent、SSE 和统一业务 API |
| 数据 | PostgreSQL + Drizzle | 事务、结构化学习历史和迁移 |
| 契约 | 运行时 Schema + TypeScript | 前后端和模型输出同时校验 |
| Agent | Pi Agent Core + Pi AI 显式 Provider | 复用模型接入、工具循环和流式事件，宿主控制配置 |
| 资料 | 首版本地受控存储；有需要再用 S3 兼容存储 | 自用无需先引入对象存储，原文件与解析结果仍分离 |
| 任务 | 初期数据库任务记录与后台执行器 | 解析、模型调用和可恢复工作 |
| 测试 | Vitest + Playwright | 领域、接口和网页闭环验证 |

这些是工程建议，不是已经安装的依赖。依赖发布版本、许可证和安全性在工程初始化时核实并锁定。

### 5.2 架构

          │
          ▼

生产部署建议通过同源反向代理连接网页和 API，避免不必要的跨域与鉴权复杂度。

## 6. Pi 集成方案

### 6.1 选择边界

| 本地模块 | 能力 | 本项目用途 |
|---|---|---|
| `pi/packages/ai` | 模型配置、提供商适配、模型响应 | 推荐复用 |
| `pi/packages/agent` | Agent 循环、工具、订阅、取消 | 推荐作为学习 Agent 核心 |
| `pi/packages/coding-agent` | 编程助手会话、扩展、资源发现 | 可用于短期验证，不作为默认完整运行环境 |
| `pi/packages/server` / `client` | 实验性服务协议、会话路由 | 暂不作为网页后端基础 |

本地 `server` 文档将其标为实验性，鉴权等仍需应用自行实现。不能把它当成开箱即用的生产 Web 服务。

### 6.2 显式 Provider 接入

在 `learning-agent` 中包装 `@earendil-works/pi-agent-core` 和 `@earendil-works/pi-ai`，仅使用公开导出接口，不跨包导入内部 `src/` 文件。按固定版本的 Provider API 接入，不复制旧版本的全局模型注册或 CLI 配置方案。

建议初始化顺序：

1. 校验应用自己的服务端配置：Provider ID、模型 ID、认证来源、端点及预算策略。
2. 从 `@earendil-works/pi-ai/providers/<provider>` 显式导入所选工厂，例如 `anthropicProvider` 或 `openaiProvider`；这些仅是 API 示例，不代表已经选定厂商。配置值只能选择代码白名单中的工厂，不能拼接任意导入路径。
3. 从 `@earendil-works/pi-ai/models`（也可包根导出）使用公开 `createModels()` 创建应用独立的 `Models` 集合，通过 `models.setProvider(...)` 注册批准的 Provider。首版只注册实际启用项，不使用旧版 `compat`，不默认使用 `providers/all` 或自动启用机器上所有可用厂商。
4. 通过 `models.getModel(providerId, modelId)` 取得明确模型，验证存在性、对话 / 工具能力与认证配置，并作为 `Agent` 的 `initialState.model`；缺失时返回配置错误，不静默选择其他模型或回退到个人凭据。
5. 以 `models.streamSimple.bind(models)` 为底层调用入口，在宿主 `streamFn` 适配器中施加请求参数、取消信号、重试策略、预算准入与用量记录，再注入 `Agent`。适配器保留传入的必要 options 并返回事件流，不用最终消息对象替代事件流。
6. 设置受控系统提示、白名单工具和当前任务上下文，用 `Agent.prompt()` 执行、`subscribe()` 观察、`abort()` 请求取消；公开事件经宿主转换后发往网页。

认证由应用自己的 `CredentialStore` 和 `AuthContext` 控制，不读取 `~/.pi` 的个人 `auth.json`、模型文件、技能或扩展。`createModels()` 默认使用独立内存凭据库，但默认认证仍可能查询环境；建议通过 `createModels({ credentials, authContext })` 注入项目独占凭据源，`AuthContext.env` 只提供批准的项目配置，其他名称返回 `undefined`，未授权本地文件探测返回 `false`。

显式传入 `apiKey` 不代表完全跳过 Provider auth：在对应 API-key handler 存在时，虽可跳过存储凭据读取，仍会调用其认证解析器。`env: {}` 也不是隔离开关，未提供的值仍可能回退到进程环境。所选 Provider 的额外请求头、端点、底层 SDK 环境 / 本地凭据链都要核实；严格隔离还需使用只含批准配置的运行环境，不能单靠 AuthContext 声称沙箱安全。

缺少批准的认证配置时，在进入 Provider 调用前拒绝请求；无密钥本地服务必须单独显式配置，不能由缺失密钥推断。

如以后使用未内置的兼容端点，优先在应用适配层通过公开 `createProvider()` 组合模型目录、认证与 API 实现；不为更换厂商直接改 Pi 核心。端点、密钥和 Provider 选择仅由服务端配置，浏览器不能任意覆盖。

每个学习 / 复习会话独立维护可变对话状态和活动 Agent 实例；可以按权限从数据库加载本人相关历史，但不能复用另一个活动会话的消息数组。Agent Core 不替应用提供账号、数据库业务记忆、复习算法或自动恢复，这些能力由宿主实现。

### 6.3 上下文与长期记忆

模型一次需要的内容包括当前会话、学习范围、相关资料片段、相关知识状态和必要的作答证据。不要把用户全部历史和整个文件库每轮都发送给模型。

- 数据库保存权威业务状态和已完成消息。
- 对话摘要只帮助压缩上下文，不能覆盖原始证据。
- 历史恢复从已提交的数据构建上下文，不以浏览器传入历史为准。
- 摘要、知识点和资料片段都保留来源或版本。
- 早期用数据库检索和来源定位即可，不强制向量检索。
- “一个 Agent、多种任务模式”不等于所有模式共用完整历史。出题答案、私有评分标准和内部评价上下文不得直接带入作答前的公开追问模式；按任务重建最小上下文。

### 6.4 Coding Agent SDK 备用路线

若用 `createAgentSession()` 快速验证：

- 显式配置工具、模型、设置和资源加载器。
- 不加载开发机器上的个人凭据、技能、扩展和项目提示。
- 禁用 Bash、任意文件读写、代码执行及其他无关能力。
- 不把默认 JSONL 会话文件当作学习业务数据库。
- 使用 `SessionManager` 管理 SDK 会话；直接改底层消息不能替代其持久化上下文。
- 宿主需要确认运行完全结束时，使用 SDK 的 settled 语义，不误把一次 `agent_end` 当成所有重试都已结束；settled 仍不等于业务成功。
- 首版关闭不需要的 cache warming（`cacheWarming: "off"`），自动摘要和重试若开启也计入预算，不能只统计用户提交次数。
- 正常清理顺序为请求取消、在有时限的清理窗口内等待收敛，再解绑订阅并 `dispose()`。`dispose()` 本身不保证等待任务结束；超时执行按第 6.6 节防止迟到写入。

长期建议仍是底层 Agent 加独立业务服务，而不是深度改造编程助手。

### 6.5 依赖策略

优先采用经核实可获取、通过适配测试的发布包，锁定应用直接依赖和 lockfile。若确需本地源码调试，单独记录构建和链接方式，不能假定 clone 后已有 `dist/` 或完整依赖。

升级 Pi 时验证工具 Schema、事件映射、取消、Provider 注册、认证隔离和历史恢复。尽量通过适配层消化变化，不修改 Pi 核心。

### 6.6 运行结束、成功和取消

本地版本的 `prompt()` 运行错误可能被转换为失败消息；`error`、`aborted` 同样会发出 `agent_end`。因此“Promise 返回”“出现 agent_end”或 `finishTurn({ action: "end" })` 都不能直接映射成业务成功。

成功必须同时满足：

- 最终 `stopReason` 与任务协议符合预期；`error`、`aborted` 不成功，`length` 按截断处理并走有限重试或失败路径。
- 完整任务输出、工具结果和业务引用校验通过。
- 本次活动运行、执行尝试和预期业务版本仍有效，数据库提交成功。

仅在上述条件成立后标记 `AgentRun.succeeded` 并发送 `run_completed`；任务成功也不代表整个学习会话已经完成。

`abort()` 只请求取消，不回滚副作用，也不能强制终止不响应信号的工具。所有网络、工具与事件订阅回调都要有有限等待和取消处理；不可让慢 SSE 客户端阻塞 Agent 收敛。`waitForIdle()` 必须放在宿主清理期限内，而非无限等待。

取消、超时或租约接管后，以数据库中的 `runId`、`attemptId`、租约与预期版本阻止旧执行器提交。超时不等于底层请求已经停止，不能在旧执行仍有写入资格时盲目重启。已提交副作用仍以数据库为准，重试靠幂等规则恢复。

### 6.7 请求限额与费用边界

通过宿主 `streamFn` 对每次真实 Provider 请求设置 `maxTokens`、`timeoutMs`、`maxRetries` 等公开选项，保留并透传取消 signal，整次任务期限另由宿主调用 `agent.abort()` 控制。这些请求选项不是直接设置在 `AgentOptions` 上；`maxRetryDelayMs` 只限制重试等待，不代表重试次数。

底层行为以所选 Provider 的公开类型与适配测试为准。部分推理模型会在 `maxTokens` 基础上加入 thinking budget，因此还要核实最终有效输出额度和推理费用，不能把一个通用 token 配置宣传为所有模型的绝对输出或费用上限。

统计工具循环中的每次模型请求、输出修复和显式重试；若 Provider 内部重试不能逐次观察，记录该限制并按配置预留预算，不宣称精确费用。启用日预算时跨会话检查，不能通过多开页面绕过；当前用户明确不设金额预算，不移除调用次数等其他限制。取消、超时和费用未知的请求同样保留记录，不视为零费用。

## 7. 业务流程与状态机

### 7.1 区分草稿、流程和后台任务

- **复述草稿**：用户可以编辑的三段内容和附件引用。
- **提交快照**：一次提交对应固定文本、资料版本和配置。
- **学习流程**：基于快照执行确认、追问和考核。
- **后台任务**：一次解析或模型运行，具有独立执行状态。

建议流程（`DRAFT` 属于复述草稿，不要求预先创建 LearningSession）：

```text
DRAFT ──提交快照──→ CONFIRMING → CLARIFYING → QUIZ_READY → QUIZZING
                       │            │              │          │
                       └─无测验结束─┴─→ SUMMARIZING ←┴─交卷/明确结束─┘
                                            │
                                            ▼
                                        COMPLETED
```

补充资料改变当前范围时，`CLARIFYING → CONFIRMING` 重新确认；已保存的问答不重写。题集保存后不再改写其范围，新增内容进入后续版本或新会话。

任务状态单独使用 `pending / running / succeeded / failed / cancelled`。任务失败或取消不直接把业务会话改成完成状态；离页暂存保留当前步骤，不等同主动结束。

### 7.2 转移规则

| 转移 | 条件 |
|---|---|
| 草稿提交 | 内容通过校验，保存快照，建立会话初始范围版本 |
| 知识确认进入追问 | 最小范围已确认；争议部分独立标为待核对，不进入确定答案的正式考核 |
| 追问进入出题 | 用户选择完成或跳过追问，有可考核范围，记录未完成部分 |
| 测验就绪 | 完整题集和私有评分标准通过校验并保存，绑定固定 `scopeVersion` |
| 无测验结束 | 用户确认范围不足或不进行考核；停止活动运行，进入总结，不伪造题目、成绩或掌握证据 |
| 交卷或提前结束 | 已提交答案取得评价或明确待核对状态；用户确认将未提交题标为跳过，运行中评分不能伪装成完成 |
| 完成 | 保存反馈、完成原因、实际存在的证据与符合条件的初始卡片状态；无有效证据时不制造复习事件 |

`completionReason` 至少区分 `assessed`（按流程交卷）、`no_quiz`（未进入测验）和 `user_ended`（主动提前结束）。它描述流程，不代表答对；是否通过或掌握由有效证据另行判断。无考核证据的记录仍可保存，但不得计入考核通过率的有效样本。

AI 可以建议下一步，不能绕过状态机。用户跳过追问时允许继续，但不能据此宣称已完整学习。结束与取消运行使用不同命令：取消只影响执行任务，结束才推进业务流程。

### 7.3 恢复与版本

- 草稿使用防抖保存和版本号，避免多标签页覆盖。
- 提交后编辑原内容形成新版本，不修改旧题目的依据。
- 资料仍在解析时，用户明确选择等待或暂不纳入；解析完成不偷偷改变当前范围或已生成题集。
- 当前问题、已答题、草稿答案、完成原因和任务状态持久化，刷新后可恢复。
- 同一学习 / 复习会话最多一个活动模型运行；并发输入返回明确冲突或复用已有运行，不由浏览器自行启动第二个运行。
- 重试复用请求标识，避免重复题集、重复评分和重复排期；不同请求对同一复习卡的并发另按第 13.6 节处理。

### 7.4 追问中补充资料与范围版本

提交快照保留最初复述；`scopeVersion` 描述当前会话已选择的资料版本、知识点版本及确认决定，两者不能混为一个可覆盖字段。

1. 新粘贴 / 上传的笔记先保存、解析，不自动加入模型可用范围。
2. 用户明确选择纳入后，以预期会话版本建立新的范围版本，必要时回到确认步骤；有活动模型运行时先取消并处理其提交资格，不能让它按旧范围提交新问题。
3. 原问题、回答和证据继续引用旧范围版本，后续问题才使用新范围。已保存的测验不因补资料被重新定义。
4. 接受 AI 补全只新增带来源的补全记录，不覆盖原始复述；是否进入考核范围仍需明确确认。
5. 题集已生成后希望考核新增内容时，保留旧题集并创建后续会话，不偷偷替换尚未作答的题目。

## 8. Agent 任务与工具设计

### 8.1 先一个 Agent，多种任务模式

| 模式 | 输入 | 输出 |
|---|---|---|
| 提取与确认 | 复述、选定资料、相关历史 | 候选知识点、来源、冲突、待确认范围 |
| 追问 | 范围、已问问题、用户回答 | 一个下一问题或建议结束 |
| 评价与补全 | 问题、回答、资料 | 评价建议、证据、不确定项、可选补全 |
| 出题 | 确认范围、薄弱点、题量配置 | 完整题目、答案、评分标准与来源 |
| 简答评分 | 固定题目、评分标准、作答 | 分项分数、依据、反馈和待核对项 |
| 总结 | 经代码计算的统计和证据 | 学习总结及建议 |

固定任务可直接调用模型，不必全部进入可自由调用工具的循环。第一版不实现多个自治 Agent 相互讨论。

### 8.2 业务工具白名单

建议工具：

- `get_learning_context`：读取本次范围及当前用户相关状态。
- `get_source_excerpt`：按资料 ID 和片段定位读取已授权内容。
- `propose_knowledge_points`：提交候选知识点，业务层校验后存为候选。
- `propose_assessment`：提交评价建议，业务层按固定标准验证。

不提供任意 SQL、路径读取、命令执行、代码执行、无限网络请求和直接“设为已掌握”的工具。

工具的用户身份来自已鉴权的服务端上下文。模型传入其他用户 ID 或越权资源 ID 时不能获得访问权限；自用也不接受浏览器指定任意用户身份。

`propose_*` 工具保存的是带运行 / 尝试标识的候选或评价提案，不能直接更新最终掌握证据和排期。任务成功校验后由宿主提交有效结果；失败运行的暂存提案不得自动生效。

本地 Pi 默认同批工具并行执行，“同一会话只有一个 Agent 运行”不保证工具串行。首版建议设置 `toolExecution: "sequential"`；以后放开只读并行时，写入或有先后依赖的工具仍声明 `executionMode: "sequential"`。这只约束当前运行，写入事务还必须检查运行资格、预期版本与业务幂等键，不能仅依赖工具预检。

### 8.3 输出契约

模型输出使用运行时 Schema 校验，至少约束：

- `schemaVersion`、允许的输出类型、枚举和文本长度。
- 知识点与来源 ID 必须属于本次授权范围。
- 分项评分范围、总分计算和引用完整性。
- 题量、选项、正确答案和评分标准一致性。
- 明确的 `needs_verification` 等待核对状态。

模型输入 Schema 不代表输出天然可靠。完整输出通过校验后才提交；不能根据尚未完成的流式 JSON 修改学习状态。

Pi 的工具参数校验包含类型转换；当前纯 JSON Schema 路径下，要求数值的字段可能把 `null` 转为 `0`。评分、评级和证据状态必须额外对原始 `toolCall.arguments` 做不强制转换的校验，例如在 `beforeToolCall` 中检查原始参数，而不是只检查已转换的 `args`。缺失、不确定或非法类型不得被默认值掩盖；未知评分保留 `null` / 待核对语义，不成为合法零分。

允许有限次数的输出修复，失败后保留用户输入并提供可重试状态，不创建无限纠错循环。

### 8.4 提示词管理

提示词放在 `packages/learning-agent/prompts/`，按任务分文件，并记录版本。

通用要求：一次只问一个问题；不要在作答前泄漏答案；区分用户自述、资料引用和 AI 推断；资料冲突先澄清；补全需用户选择；无依据不输出精确百分比。

生产流程由代码加载确定的提示词，不依赖模型是否自动读取某个 Pi Skill。Skills 可在后期用于扩展学科策略，但不能作为权限或必执行步骤的唯一保障。

## 9. 数据模型与持久化

### 9.1 核心实体

以下是逻辑模型，初始化迁移时按实际读写路径确定表结构，不要求每一项单独一张表。

| 实体 | 主要字段 / 职责 |
|---|---|
| User | 身份、时区、学习偏好、访问配置 |
| Recitation | 用户、当地学习日期、三段文本、主题、草稿版本、提交快照 |
| SourceDocument | 用户、归属复述、类型、文件键、内容哈希、版本、解析状态 |
| SourceExcerpt | 资料版本、文本、行号 / 标题 / 偏移、提取方式；后续 PDF 再增加页码 |
| LearningSession | 快照、流程状态、完成原因、当前步骤、配置、活动运行、当前范围版本 |
| LearningScopeRevision | 会话、`scopeVersion`、资料版本、知识点稳定 ID 与内容版本、逐项确认 / 拒绝 / 争议决定 |
| FollowUpTurn | 问题、回答、类型、辅助情况、评价版本、范围版本、知识点引用 |
| KnowledgePoint | 稳定 ID、用户、名称与别名、主题、内容版本、用户理解、来源引用；本次是否纳入由会话范围记录 |
| KnowledgeEvidence | 知识点与目标版本、作答 / 复述引用、记忆 / 理解 / 应用维度、评价与辅助标记 |
| Quiz / Question | 测验类型、范围版本、所属学习 / 复习会话、顺序、题干、难度、私有答案、评分标准、版本 |
| Answer / Assessment | 草稿与正式作答状态、原始答案、跳过、用时、评分各版本、申诉、最终采用版本 |
| Misconception / Supplement | 误解及后续验证；AI 补全、来源和 `accepted / self_reported_known / deferred / rejected` 决定 |
| ReviewCard | 稳定回忆目标、目标版本、排期状态、并发版本、算法与参数版本 |
| ReviewSession | 卡片、初始卡片版本、来源流程、当前步骤、回忆草稿 / 提交、题集、辅助标记、活动运行、实际作答时间与完成状态 |
| ReviewEvent | 所属复习会话、采用的评分版本、有效评级、实际复习时间、前后卡片状态；一次目标级排期事件 |
| AgentRun | 请求标识、执行尝试与租约、任务类型、Provider / 模型、提示词版本、状态、费用与错误 |

可另设领域事件记录，形成“复述中出现 → 追问确认 → 测验作答 → 延迟复习”的轨迹。活动状态可更新，历史证据应保留版本。

### 9.2 重要约束

- 所有用户内容和查询具备用户归属约束；自用可只有一个用户，但不移除外键和授权检查。
- 若采用每日一份复述，按 `(user_id, learning_date)` 设置唯一性；多次提交使用版本和子会话。
- 资料片段引用资料版本，而非仅引用会被覆盖的文件名。
- 草稿可按版本更新；同一题目的正式提交具备唯一约束，提交后不再以草稿覆盖，申诉创建评分新版本。
- `(session_id, scope_version)` 唯一，问题和证据引用当时的固定版本；知识点名称不作为全局唯一键。
- 一个回忆目标可复用稳定卡片，重复提取或新日测不能重置已有卡片状态。
- 同一 ReviewSession 最多产生一个有效排期事件；同一卡片最多一个未关闭复习会话，数据库约束或事务保证，不能只靠按钮禁用。
- 卡片更新检查 `expectedCardVersion`，不同请求、不同流程也不能基于同一个旧版本重复推进排期。
- 时间戳用 UTC 保存；学习日期、到期日和周统计按用户时区计算。
- 应用配置、Provider / 模型、提示词、评分规则和调度算法均记录版本。

### 9.3 知识状态

分别保存：

- 本次范围确认状态：候选、已确认、争议中或拒绝，绑定会话与知识点版本；不能因昨天确认过就默认今天的新内容已确认。
- 用户自评：例如“觉得已经掌握”。
- 测量证据：独立或辅助作答及对应能力维度。
- 误解状态：待核对、已确认误解、本次改正、延迟验证。
- 覆盖状态：已提及、未提及、超出本次范围。

界面可以派生“待巩固”“有误解”等标签，但规则需确认并版本化。没有证据时不要为了标签数量完整而设成“已掌握”。

### 9.4 事务边界

原始正式答案先独立保存，再启动评价任务；模型超时或取消时答案仍存在，评价保持待处理。评价和相应知识证据在同一事务中提交，不能假装评分成功。

正常作答路径由目标级 ReviewSession 完成命令聚合有效评价，并在一个事务内提交复习事件、会话完成状态和卡片版本更新；不能每评完一道题就推进一次间隔。新目标的初始卡片按唯一规则创建，既有卡片不因学习会话完成而重复初始化；已生效评价的纠错另走第 13.3 节的受控复算事务。

异步任务入库与业务命令避免双写丢失：初期可在同一数据库事务中建立任务记录，执行器通过状态和租约领取，不只依赖进程内 Promise。所有异步写入再次检查活动 `runId`、`attemptId`、租约和预期业务版本，防止取消或接管后的旧结果落库。

历史记录用于审计，不代表无限保存用户原文；隐私删除仍需覆盖相关存储和日志。

### 9.5 跨天知识点复用

例如今天提取“缓存穿透”，明天提取“Redis 缓存穿透”，不能仅因名称不同就创建第二张卡，也不能仅因名称相似就自动合并。

- 每次提取先查当前用户的已有知识点，按规范化名称、别名、主题和回忆目标给出匹配候选；首版不依赖向量数据库。
- 用户确认复用哪个稳定 ID 或创建新知识点。对话中的候选 ID 与正式稳定 ID 分开，模型建议不能直接迁移历史。
- 仅修正描述、来源或“我的理解”时新增内容版本；已有证据仍引用原版本，不自动清空排期。
- 回忆目标实质改变时创建新目标 / 卡片，并显式决定旧卡是否继续使用；首版不实现自动拆分、合并或迁移评分历史。
- 同一知识点在不同学习会话中的确认决定分别记录，历史身份复用不等于本次范围自动确认。

### 10.2 请求规则

- 身份由服务端会话确定，不相信请求中的任意 `userId`。
- 写请求携带幂等键；草稿和流程命令携带预期版本，范围修改检查 `scopeVersion`，排期修改检查 `expectedCardVersion`。
- 幂等键绑定用户、操作与请求内容，同键不同内容不能复用旧结果。
- 长运行任务返回 `202` 与 `runId`，业务内容通过已保存状态和 SSE 获取。
- 错误使用稳定业务码，例如 `VERSION_CONFLICT`、`CARD_VERSION_CONFLICT`、`RUN_IN_PROGRESS`、`MODEL_NOT_CONFIGURED`、`MODEL_UNAVAILABLE`、`BUDGET_EXCEEDED`。
- Provider / 模型不匹配或缺少认证配置时失败关闭，不静默换厂商、换模型或调用开发机凭据。
- 前端错误提示保留输入，不直接展示内部堆栈或提供商凭据。

### 10.3 SSE

建议事件信封包含 `eventId`、`runId`、`sequence`、`type` 和 `payload`。

公开事件例如：`run_started`、`assistant_text_delta`、`question_ready`、`evaluation_ready`、`document_status_changed`、`state_changed`、`run_completed`、`run_failed`、`run_cancelled`。

- 只转发面向学习者的内容，不透传 Pi 原始事件。出题、评分和结构化提取模式不直接公开原始文本增量，只发布验证后的学习者 DTO。
- 评分内部输出、未公开答案、工具私有结果和模型推理不进入公开流；不能靠前端隐藏已收到的私有字段。
- `run_completed` 只在任务校验和数据库提交成功后发布，`agent_end` 不直接映射为成功；取消与失败也分别保留实际终态。
- 断线后从持久化快照恢复；有事件保留窗口时按序续传，客户端按事件 ID 去重。
- SSE 连接断开不等于任务取消，取消由明确命令触发。
- 使用同源 Cookie 或支持鉴权头的流式请求；不把访问令牌放进 URL。
- Cookie 写接口具备 CSRF 防护；SSE 同样校验用户对运行的访问权。

### 10.4 关键交互命令契约

下表约定语义；字段最终由 `contracts` 的运行时 Schema 定义，成功响应返回资源 ID、最新版本、当前状态和必要的 `runId`，不让前端猜测下一步。

| 交互 | 关键输入 | 持久化与限制 |
|---|---|---|
| 知识确认 / 复用 | 候选 ID、决定、可选已有知识点 ID、内容版本、预期范围版本 | 校验归属，保留逐项决定；修改范围形成新版本，不迁移旧证据 |
| 纳入 / 移除资料 | 资料 ID 与版本、动作、预期会话版本 | 只接受已授权资料；纳入须解析完成，旧题集不变 |
| AI 补全决定 | `accepted / self_reported_known / deferred / rejected`、预期版本 | 接受生成独立补全记录；自评不增加掌握证据；稍后也保存决定，不反复强推 |
| 我的理解 | 文本、预期知识内容版本 | 新增修订，旧作答依据不变，目标改变按第 9.5 节处理 |
| 答案草稿 | 草稿文本 / 选项、预期版本 | 仅限未提交题，不触发评分；暂存退出前等待保存确认，失败保留本地输入 |
| 正式作答 / 跳过 | `answer / skip`、题目版本、辅助标记、作答内容 | 幂等保存，提交后不可改；跳过不计成错误，查看讲解后记录已暴露 |
| 交卷 / 主动结束 | 预期会话版本、明确确认未答题处理、结束原因 | 不把草稿自动当正式答案；未确认的未答处理返回冲突，保留原输入 |
| 复习回忆 | `draft / submitted`、文本、预期复习会话版本 | 草稿可改，正式提交固定；空白回忆需明确记为未回忆 / 跳过，不伪造正确证据 |
| 复习完成 | 复习会话 ID、预期会话 / 卡片版本 | 评级和新排期由后端已存评价计算，不信任浏览器传来的分数、间隔或日期 |

AI 补全的移除通过其独立资料记录处理，保留曾接受与后来移除的历史，不改写原始复述。历史查询以用户时区和日期范围取记录，再选择具体快照；查看昨日复述不依赖浏览器保存的旧 URL。

## 11. 笔记上传与资料处理

### 11.1 处理链路

```text
文件 / 粘贴输入 → 权限和格式校验 → 原文存储 → 解析任务
              → 来源片段 → 用户确认纳入范围 → 提取与出题
```

粘贴笔记作为独立资料保存，不自动覆盖复述正文。原始复述、用户笔记和 AI 补全是不同来源类型。

### 11.2 首期 TXT / Markdown 解析约束

- 首期白名单为 `.txt`、`.md`、`.markdown`；不接收 `.mdx`、压缩包、PDF、DOCX、图片或可执行文件。上传与粘贴受同样的文本资源限制。
- 校验扩展名、MIME 合理性、字节数、数量和可解码性。纯文本没有可靠的统一魔数，不能只看 MIME 或伪称通过文件签名就安全；拒绝明显二进制、NUL 和不可解码输入。
- 建议首版使用 UTF-8（允许 BOM），其他编码提示用户转换，不静默乱码解码；最终编码策略与限制在 P0 确认。
- 后端生成文件键，不能让文件名控制服务器路径；限制单文件字节数、总量、抽取字符数、内存和耗时。
- 保存原文件及哈希，规范化换行后切片并保留定位。Markdown 按非可信内容渲染，不执行 HTML / 脚本，不自动抓取外链或加载外部图片。
- 基础解析也有任务状态、失败原因和重试入口，不产生空白“已解析”资料；没有可靠进度时显示“解析中”，不伪造百分比。
- 从当前资料集合移除后停止新任务使用；这与彻底删除个人数据不同。前者保留旧快照依据，后者按删除政策清理原文与派生内容，历史可显示来源已删除。

设计包的单文件 20 MB、每日 10 个不是已确认限制；实际页面说明来自服务端能力配置。PDF / DOCX / OCR 若后续获准，再增加页数、解压后大小、宏 / 嵌入内容和解析隔离约束，不作为首期上传的依赖。

### 11.3 来源定位

首期保存资料版本、Markdown 标题或 TXT 行号、规范化文本偏移和摘录，引用显示“笔记第 12–18 行”等，并允许查看原文。以后支持 PDF 再补页码，不让 TXT / Markdown 伪装成具有页码的文档。

用户原文、解析文本与模型推断分别标注；以后新增 OCR 时另标提取方式。资料间有冲突时展示双方来源，不能默认笔记永远正确。

首期不抓取用户粘贴的任意外链。未来若支持 URL 导入，另行设计 SSRF 防护、来源许可和访问限制。

## 12. 出题评分与掌握证据

### 12.1 出题范围

- 已确认的学习目标、明确薄弱点和到期回忆目标。
- 对待核对内容不生成带确定答案的正式考核，先解决来源冲突。
- 用户拒绝的补全不悄悄进入已学范围。
- 拓展题明确标记为拓展，不用于判定用户是否掌握原有范围。

题目生成后，题干、答案、评分标准、资料依据和版本一起固定保存。作答之后不能由模型重新定义标准来迎合作答。

### 12.2 题型与判分

MVP 使用单选和简答：

- 单选由代码依据固定答案判定，AI 只负责生成及讲解建议。
- 简答先定义关键概念、必要推理和允许表达，再按分项标准评价。
- 简答总分由代码根据合法分项得分计算，不盲信模型总分。
- 表达方式不同不自动判错；关键概念缺失、结论矛盾要引用作答依据。
- 无法可靠判定时显示待核对，不能只用模型自报“置信度”作最终裁决。
- 自动申诉与复评在 P3 实现，保留原评分，复评形成新版本，并明确最终采用哪一版；首版仍需提供记录争议和人工核对的操作路径，不能把待核对结果强制认定为正确评价。

复杂推导和用户代码执行后续另行设计，不能直接在 API 主进程运行用户代码。

### 12.3 学习表现标记

每次作答记录：是否独立、是否打开提示、是否查阅资料、是否已见答案、是否跳过、题目版本、评分版本。区分应用内可观察的辅助行为与用户自报；自用应用不宣称能够证明用户未在应用外查资料。

建议区分：

- **训练表现**：提示、讲解或笔记帮助后的回答。
- **即时考核**：当天独立回答。
- **延迟回忆**：经过时间间隔后的独立回答。

这三类不能直接等价。一次日测中的同一目标多题只形成受控的综合证据，不把每题当成一次独立间隔复习。

### 12.4 防止答案泄漏

设计包采用练习模式的即时反馈，后端应：

- 只提供当前题和允许回看的已答题；设计中下一题预览只是样式参考。
- 作答前不发送 `correctOption`、参考答案、私有评分细则或内部工具内容。
- 答案提交成功后才公开对应反馈。
- 前面题目的讲解泄漏后续目标答案时，把后续表现标为已暴露，避免误当独立证据。

若以后提供考试模式，需单独定义交卷前不反馈规则，不与练习模式混用。

练习模式仍区分草稿、正式作答与交卷：单选沿用“选择即正式提交”，提交成功后锁定；简答先保存草稿，点击提交才评分。按顺序答题，可明确跳过当前题后进入下一题，不允许任意跳到未来题查看。跳过与未答均不计成错误。

暂存退出只保存进度，不自动交卷、不评分草稿；离页暂停展示计时，耗时不作为独立掌握证据。交卷前确认未提交题的处理；结果页展示已完成评分、跳过和待核对项，评分失败保留原答案并允许重试。

评价已完成或明确标为待核对后，日测交卷推动所属 LearningSession 进入总结；复习测验交卷只推进所属 ReviewSession 到 `READY_TO_COMPLETE`，仍须按目标完成命令统一提交排期。主动提前结束复用同一收尾规则，不另写一套隐式交卷逻辑。

### 12.5 指标口径

优先显示独立作答正确率、简答得分、辅助次数、误解与延迟回忆结果。

客观题正确率、简答平均得分和模型预计保持率分别展示。空样本使用 `null` 或“暂无数据”，不显示 0% 误导用户。

完整度只有在参考课程范围和分母明确时才计算；若仅来自 AI 临时猜测，应标为覆盖建议而非客观百分比。综合掌握度须经产品确认、保留公式版本及证据数量。

## 13. 间隔复习与曲线展示

### 13.1 推荐 FSRS

艾宾浩斯曲线提供遗忘与复习的设计启发，不是每个用户共享的固定时间表。

建议采用维护良好、经核实版本的 FSRS 实现，初期使用默认参数；不自行拟合示意指数曲线，也不在少量样本下训练个人参数。

设计令牌中的 `review` 配置不得成为生产调度规则。若先做固定间隔演示，必须标明演示，不能与真实排期混用。

### 13.2 复习对象

一个复习卡对应明确且尽量稳定的回忆目标，可关联一个知识点和多个变式题。不是每篇笔记一个卡，也不是每道临时题一个独立卡。

同一目标的复习题保持大致可比难度。高难应用题单独评估理解，不简单将失败解释为遗忘。

### 13.3 更新过程

```text
初始化目标 → 到期 → 独立复述 / 回忆 → 作答
          → 判断辅助与证据有效性 → 形成一次复习结果
          → 调度算法更新 → 保存事件与新状态
```

- 首次学习按目标初始化新卡；复用已有目标时不重置其排期。没有考核证据时最多保存明确的未验证新卡状态，不伪造正确评级或复习事件；当天反复练习不能冒充多次延迟复习。
- 评分到调度评级的映射要在 P2 前显式定义并版本化，不把“85 分”直接等同“容易”。确认 FSRS 实现、目标保持率、学习 / 重学步骤及 `Again / Hard / Good / Easy` 的适用条件；参数未确认时只做假时间测试，不启用真实自动排期。
- 自动讲解后答对不记成独立“容易”；用户主观难度可单独记录。
- 多题复习聚合成一个目标级事件；无有效证据的中断不推进间隔。
- 题目难度、辅助情况和不可判定结果参与映射规则。
- 提前复习按真实作答时间执行算法，不偷偷改成到期时间；模型评分延迟时不以评分任务结束时间冒充回忆发生时间。
- 算法版本、参数版本、前后状态与生效评分版本保留，便于复算。

评分申诉影响已生效排期时，从相关有效事件按顺序复算或使用明确的修正规则，不能再次追加同一次复习来重复奖励。

### 13.4 队列

优先逾期项目，其次依据到期时间和可用的风险估计排序。没有可用保持率时按到期时间排序，不补随机百分比。

手动调整只改变允许范围内的展示顺序，不修改算法状态。每日负荷过高时可限制新卡或建议分批，但不要静默把逾期项目伪装成未来未到期。

### 13.5 记忆曲线

- 曲线属于模型估计，不是直接观察到的真实保持率。
- 历史估计、复习作答记录和未来假设分别标注。
- 未来曲线说明假设，如“按计划完成复习且达到预设表现”。
- 不为复刻截图而把每次复习后的真实保持率宣称为 100%；若所用算法在零间隔处数学上取 1，也明确标为模型假设，不当作观测证据。
- 缺少参数或历史时显示暂无估计，附实际复习时间线。
- 若保留设计的平方根时间轴，显示轴说明；展示变换不改变调度时间。
- 提供文字节点列表作为图表替代。

MVP 先展示真实复习时间线与到期日期，不要求实现完整预测曲线。曲线启用时才按以上规则验收。

提醒与排期独立：提醒失败不修改复习结果；通知渠道、提醒时间和重试上限另行确认。

### 13.6 复习会话与并发更新

单张卡的建议流程：

```text
RECALLING → QUIZ_READY → QUIZZING → READY_TO_COMPLETE → COMPLETED
    └──────────────明确放弃──────────────→ ABANDONED
```

任何未完成步骤都可明确放弃；离页只是暂存，仍保留当前步骤供恢复。题集生成、评分和失败重试由独立任务承载，不用任务成功状态代替复习会话状态。

- `start` 记录卡片 ID、目标版本、`expectedCardVersion` 与来源流程；同一卡已有未关闭会话时返回该会话，不另建第二份。暂停的会话可恢复或明确放弃后重开。
- 先保存独立回忆，再生成 / 展示可比难度的题集。题量配置化，设计稿的 2–3 题不是固定要求；若提前提供讲解或提示，后续作答记录为已辅助 / 已暴露。
- 多题作答复用测验接口，但明确属于哪个 ReviewSession。每题评分只保存证据，完成时才聚合一次目标级结果。
- `complete` 在事务中检查会话状态、采用的评分版本与卡片版本，成功后写一个 ReviewEvent 并更新卡片；无有效证据时关闭会话但不推进排期。
- 同一完成命令重试返回已保存结果；另一命令基于旧卡片版本提交时返回 `CARD_VERSION_CONFLICT`，保存原答案供查看，不再追加评级奖励。冲突后可明确放弃旧会话再开始，不把旧证据换一个最新版本号重新提交。
- 每日测验若混入到期目标，必须关联该卡的 ReviewSession，复用同一聚合和提交逻辑；否则只能形成练习证据，不直接更新既有卡片排期。首版可先分开日测和到期复习，避免隐式双重更新。
- “开始今日复习”顺序启动队列中的单卡会话，每完成一张重新读取队列；中途退出后优先恢复未关闭会话，不依赖前端队列索引重建进度。首版无需另建复杂批次调度系统。

## 14. 前端页面与交互规范

### 14.1 页面规划

| 页面 | 建议路由 | 首版范围 |
|---|---|---|
| 今日复述 | `/recite` | 三段文本、主题、粘贴 / TXT / Markdown、提交与到期入口 |
| AI 追问 | `/sessions/{id}/ask` | 知识确认、来源冲突、单问单答、补充资料、补全决定 |
| 每日测验 / 结果 | `/quizzes/{id}`、`/quizzes/{id}/result` | 当前题、暂存、评分、交卷、结果或待核对状态 |
| 复习计划 / 单卡复习 | `/review`、`/review-sessions/{id}` | 到期队列、先回忆再答题、恢复、真实时间线；复杂曲线和周 / 月历后置 |
| 知识库 / 详情 | `/knowledge`、`/knowledge/{id}` | 理解、资料、误解、证据、下次复习 |
| 历史复述 | `/history` | 简单日期列表和只读快照，进入当时会话 |
| 学习复盘 | `/insight` | 完整统计、热力图和周报后置到 P4，MVP 不展示假数据占位页 |

知识库列表、测验结果、复习回忆、历史、个人访问和设置属于设计未完整覆盖的页面 / 状态，按上述最小职责补齐，不必先设计完整后台管理系统。

MVP 的小屏导航独立保留“今日 / 复习 / 知识库 / 历史”等入口；追问和测验从当前会话继续进入，不强行保留没有活动会话的独立标签。延期 `/insight` 不能导致知识库入口消失。具体导航排布在页面联调前确认。

### 14.2 设计实现顺序

先用假模型与假时间验证一条纵向业务闭环，再按“视觉令牌 → 最小基础组件 → 应用外壳 → 今日复述 → AI 追问 → 测验及结果 → 复习队列与单卡流程 → 知识详情与历史”实现页面。统计和复杂图表在闭环稳定后补充，不先铺满六张静态截图。

前端可先用显式 mock 数据联调组件，但模拟题目、百分比和用户记录只能出现在开发 / 演示模式，生产构建不得混入。

### 14.3 视觉与无障碍

- 颜色、字体、圆角、阴影使用交接令牌；不散落硬编码主题值。
- `primary-500` 上使用 `primary-800` 的文字和图标，不使用低对比度白字。
- 数字和中文单位按设计要求分别排版。
- 状态同时使用文字，不能只依赖红绿颜色。
- 图标按钮有 `aria-label`，所有主要交互可以键盘完成。
- 对话区使用适度的 `aria-live="polite"`，避免逐字符不断播报。
- 提供焦点样式、图表文字替代和表格查看入口。
- 响应式按交接包的 1280、1024、768 断点实现；小屏导航和侧栏内容保持可访问。
- 字体加载失败有回退；若外部字体服务影响可用性，评估合法自托管方案。

令牌通过设计源及生成链路维护；新增视觉需求先同步设计。业务复习参数不放在视觉令牌里。

### 14.4 状态体验

- 自动保存状态由真实保存结果决定；采用交接建议的 1 秒防抖时需处理版本冲突。
- 新用户、无到期项目、暂无评分都有独立空状态。
- 网络断开保留草稿；本地缓存以用户隔离，退出时清理，不串到另一个账号。
- AI 失败保存输入并提供重试；正在运行时禁止重复发送同一命令。
- 删除笔记、移除附件需要确认或可撤销。
- 一次只问一个问题；“完成”“跳过”说明对未完成部分的影响。
- 所有统计数值由接口提供，格式化后的日期和学习日按时区一致显示。

## 15. 安全隐私与可靠性

### 15.1 安全边界

- 模型和存储密钥仅在服务端，不进入网页公开环境变量或日志。
- 每个 API、资料读取、任务和 SSE 都校验资源归属。
- 用户笔记、OCR 和模型输出是非可信数据，不能改变系统权限。
- 用户文本及 AI Markdown 渲染做 XSS 防护；限制 HTML 和危险链接。
- 公式渲染关闭不需要的可信 / HTML 能力。
- 文件存储不公开目录；下载和预览经过授权或短期签名。
- 生产不开放开发用户、组件演示、假评分或管理调试接口。

当前已确认自用，建议首版本机运行时绑定回环地址；远程访问必须先配置单用户认证或受控访问代理，不做公开注册。具体认证机制在部署前确定，不以“自用”为理由公开无鉴权 API。

保留资源归属校验和越权测试不代表要先实现多租户产品。以后转为多人使用时，另行评估账号、滥用、隐私与运营风险。

### 15.2 隐私

向用户说明资料发送给哪些服务、用途、保留时间和删除方式。日志默认只记录必要元信息，原文与完整模型请求若需存档，应受单独授权和保留策略控制。

删除范围覆盖原文件、解析片段、派生知识、模型存档、任务数据和未来可能的索引。备份的删除生效周期也应明确。历史可追溯原则不用于拒绝隐私删除。

### 15.3 可靠性

- 每个任务有超时、重试上限、领取租约、执行尝试标识和可恢复状态；旧尝试失去写入资格后才允许接管。
- 幂等性由业务标识及数据库约束保证，不只依赖按钮禁用；不同流程对同一卡片还需版本检查。
- 重试模型调用可能增加费用，必须记录；取消不保证提供商停止计费或工具立即停止。
- 每个会话有模型请求次数、输出长度、工具次数限制及可选费用预算；Provider 请求、修复与重试统一纳入，不只数用户消息。
- 若启用预算，预算不足或价格 / 用量未知时按明确策略暂停、预留或请求确认；未设预算仍保留未知计量，不静默认为免费；保留进度，不把未完成任务当成完成。
- 后端关闭时停止新任务，在清理期限内请求取消与等待；超时后撤销旧尝试的提交资格，再交还任务，避免永久 `running` 和迟到写入。

### 15.4 可观测性

记录请求 / 会话 / 运行 / 执行尝试 ID、Provider / 模型与提示词版本、范围版本、耗时、最终 `stopReason`、重试、工具失败、Schema 校验失败和可取得的 token 使用量。

费用是提供商信息或估算，区分真实已知值和未知值；不能把缺少价格当成零成本。

## 16. 开发环境与工程约定

### 16.1 初始化顺序

1. 使用已确认的自用、显式 Provider、TXT / Markdown 范围；将真实模型和访问方式等剩余决策按启用阶段列出，金额预算当前明确不设。
2. 创建外层应用工作区，不移动或修改已有 `pi/`。
3. 固定 Node.js 与包管理器版本，核实依赖后创建 lockfile。
4. 先用 `fauxProvider` 验证显式注册、Agent 事件、失败判定、取消和原始参数校验；无需真实密钥或网络。
5. 建立领域契约、数据库迁移、配置校验与假时间测试，跑通可恢复的最小纵向闭环。
6. 导入审核后的设计资料，逐步接入页面、粘贴 / 文本上传与真实复习；真实模型仅在明确配置、理解资料外发及费用/额度风险后由用户主动调用；不设置金额预算也是显式策略。

初始安装默认禁止未审查的依赖生命周期脚本；需要执行时单独核实原因。此手册不要求此时安装或构建 Pi。

### 16.2 应用环境变量草案

以下为宿主应用计划采用的配置名，不是 Pi SDK 自带配置：

| 名称 | 用途 |
|---|---|
| `DATABASE_URL` | 数据库连接，服务端保密 |
| `SESSION_SECRET` | 登录会话密钥，服务端保密 |
| `MODEL_PROVIDER` / `MODEL_ID` | 旧显式模型配置的回退来源；网页保存的选择优先，不表示自动发现所有厂商 |
| `MODEL_API_KEY` | API-key 认证路线的服务端凭据；其他认证方式需单独配置，不默认继承开发机凭据 |
| `MODEL_BASE_URL` | 仅经批准的自定义端点使用，不能由网页覆盖或作为隐式回退 |
| `AI_MODE` | 明确区分 `mock` / `live`；生产禁止通过缺失配置自动切为 mock |
| `STORAGE_DRIVER` / `STORAGE_ROOT` | 本地或对象存储配置 |
| `OBJECT_STORAGE_ENDPOINT` / `BUCKET` | 后续对象存储配置 |
| `OBJECT_STORAGE_ACCESS_KEY` / `SECRET_KEY` | 服务端存储凭据 |
| `AI_RUN_TIMEOUT_MS` / `AI_CLEANUP_TIMEOUT_MS` | 任务超时及取消清理期限 |
| `AI_MAX_OUTPUT_TOKENS` / `AI_MAX_RETRIES` | 请求适配器的输出上限与重试策略 |
| `AI_MAX_CALLS_PER_SESSION` | 会话内全部模型请求的限制，不只统计用户提交 |
| `AI_BUDGET_PER_USER_DAY` / `AI_REQUEST_RESERVATION_USD` | 可选美元日预算与任务预留；当前均省略，若启用必须同时配置正数 |
| `UPLOAD_MAX_BYTES` / `UPLOAD_MAX_COUNT` / `SOURCE_MAX_CHARS` | 首期文本上传与抽取资源限制 |

基础配置在启动时校验；`live` 可未选择模型启动以便进入配置页，但缺少有效模型选择、认证或必要的输出限制确认时，拒绝入队和执行真实任务。不设金额预算不阻止启动；若填写预算，须同时校验日预算与预留。测试模式始终执行 faux Provider。供应商自己的配置名由适配层明确映射，不把这些宿主变量名当成 Pi 内置约定。示例文件只放占位值，真实 `.env` 不提交，公开前端配置只能包含非敏感值。

### 16.3 脚本约定

当前应用已提供 `dev`、`check`、`test:unit`、`test:integration`、`test:e2e` 和数据库维护脚本；使用方式与已运行结果见 README。

外层应用与 Pi 的检查命令分别运行。若以后修改 Pi，先完整读取 `pi/AGENTS.md`，遵循其依赖、测试和提交规则；不要无差别运行可能调用真实模型的全量测试。

### 16.4 开发规范

- TypeScript 严格模式；外部输入和模型输出必须做运行时校验。
- 数据库迁移可审查，生产不依赖自动推断改表。
- 时间、模型、调度和存储封装成可替换依赖。
- API DTO 与数据库记录分离，采用白名单序列化防泄漏。
- 提示词、评分规则和调度参数作为可版本化资产管理。
- 新依赖固定直接版本，审查 lockfile 与安全影响。
- 不擅自删除已有功能或源码，不自动提交未经要求的改动。

## 17. 开发任务与验收标准

### P0：配置、契约与免费集成验证

交付：已确认范围记录、外层工作区、显式 Provider 适配与 faux 验证、领域契约、数据库迁移、最小组件与纵向闭环原型。

验收：

- [ ] 应用工程与 Pi 源码隔离，依赖版本可复现；没有为了接入模型修改 Pi 核心。
- [ ] 不配置真实密钥也能使用 `fauxProvider` 完成假模型验证，不产生网络请求或费用。
- [ ] 显式 Provider / 模型不存在或认证未配置时明确失败，不回退到其他厂商、开发机凭据或 mock。
- [ ] 原始工具参数、串行写入、失败终态、取消超时及迟到结果阻断有适配测试。
- [ ] 开发 / 生产、mock / live 明确区分；身份、时区、预算、题量和文本限制有配置来源。
- [ ] 基础组件符合令牌和键盘访问要求，不要求先实现全部截图。

### P1：文本与附件学习闭环

交付：今日复述、粘贴笔记、TXT / Markdown 上传、知识确认与复用、追问、测验及结果、证据、知识详情和历史入口。

建议顺序：草稿 / 快照 → 文本资料保存与解析 → 范围版本和确认 → 追问与补全决定 → 固定题集 → 草稿 / 作答 / 交卷 → 总结与历史。

验收：

- [ ] 复述可以走完流程，也可暂存、跳过或无测验结束，完成原因明确且不制造成绩。
- [ ] TXT / Markdown、粘贴、格式限制、失败重试、移除和行号 / 标题引用均可用；PDF 等入口不开放。
- [ ] 补充资料需明确纳入新范围，原快照、旧问答和旧题集不被覆盖。
- [ ] 同一知识点跨天可复用，修改描述不清空历史、不创建重复复习卡。
- [ ] 候选、自评和验证证据互不混淆；补全决定与“我的理解”修改可恢复。
- [ ] 出题依据与评分标准在作答前固定，草稿不评分，正式提交不可被草稿覆盖，交卷确认未答题处理。
- [ ] 刷新和失败重试不丢输入，并发提交不产生重复题集或重复作答。
- [ ] 作答前任何公开响应、模型文本流或工具结果均不含私有答案。

### P2：复习闭环与自用 MVP 验收

交付：稳定回忆目标、经确认的调度映射、ReviewSession、到期队列、独立回忆与题集、历史时间线和最小数据管理路径。

验收：

- [ ] 假时间可验证新卡初始化、到期、逾期、提前复习及评分延迟；已有卡片不被日测重置。
- [ ] 回忆草稿、题集和作答可恢复；批量入口中断后能找到未关闭的单卡会话。
- [ ] 同一复习重试只更新一次，不同请求 / 流程基于旧卡片版本时不能重复推进排期。
- [ ] 多题按目标聚合，辅助、跳过、不可判定和无证据结束有明确映射，不伪装成独立正确回忆。
- [ ] 算法、参数、评分和前后状态版本可追溯，时区一致，队列数量与详情排期一致。
- [ ] 首版只要求真实时间线与到期日期；若展示估计曲线，明确标注并通过第 13.5 节验收。
- [ ] 已选单用户访问保护、费用限制、导出删除与备份恢复路径经过验证；可以先是受控操作而非管理页面。

P0、P1、P2 与基本安全检查完成后形成自用 MVP。真实模型只在 Provider、模型、凭据、允许外发的资料及费用策略（当前不设应用预算）已确认后接入验证；免费原型通过不等于真实模型质量已验收。

### P3：按需资料与可靠性扩展

候选交付：经批准后加入 PDF / DOCX、页码定位、题目变式、自动申诉和数据管理页面。TXT / Markdown 基础体验、基础恢复和资源限制已在 P1 / P2 完成，不重复后置。

验收：

- [ ] 新格式获准后再启用，限制、解析隔离、失败、重试和移除均有一致状态。
- [ ] 补充资料不改变历史测验版本。
- [ ] 申诉保留前后评价，必要时正确修正排期，不重复增加复习事件。
- [ ] 数据管理页面复用已验证的导出、删除和备份恢复规则。

### P4：统计与个性化

交付：统计页面、周报、提醒和后续选定的增强能力。

验收：

- [ ] 统计口径有定义和版本，基数不足明确显示；时间筛选控制哪些卡片、固定热力图范围和周报周期分别说明，不混用“近 30 天”和“本周”。
- [ ] AI 周报仅解释已核实统计，不自行编造数值。
- [ ] 通知失败不影响学习状态，费用与重生成次数受限。
- [ ] 用延迟回忆样例检查是否真正改善学习效果。

不提前承诺各阶段工期；确认范围、模型接入和设计差异后再估算。

## 18. 测试评估与上线检查

### 18.1 测试分层

- **领域单测**：状态转移、指标口径、调度评级、假时间、版本及幂等规则。
- **模型适配测试**：faux Provider 验证显式注册与认证隔离、事件转换、失败终态、取消、坏 JSON、原始工具参数和来源越权。
- **数据库集成测试**：事务、并发唯一性、任务租约与旧尝试隔离、卡片版本、评分修正和时区。
- **端到端测试**：复述到复习、TXT / Markdown 上传、补资料范围版本、刷新恢复、离线草稿、失败重试、键盘流程。
- **安全测试**：跨用户访问、答案泄漏、XSS、非法文件、资料提示注入。
- **人工模型评估**：知识提取、追问相关性、出题有效性和评分公平性。

日常自动测试默认使用假模型和假凭据，不隐式调用真实付费服务。真实模型评估需明确启用、限定预算并使用允许发送的样例。

首批必须覆盖的自动回归：

| 场景 | 预期 |
|---|---|
| 假响应返回 `error / aborted / length`，但运行已结束 | 不产生业务成功或有效评分，输入仍可恢复 |
| 评分字段是 `null` 或字符串数字，Pi 可能做转换 | 原始参数校验拒绝伪合法分数，未知不变成零分 |
| 同一批两个工具写同一旧版本 | 明确串行策略；即使使用并行测试，数据库版本检查也最多允许一次有效提交 |
| 旧执行器在取消或租约接管后返回 | 不再写入问题、评价或排期 |
| 所有候选拒绝后无测验结束 | 有完成原因，没有虚构成绩或已掌握标签 |
| 补资料、保存答案草稿、正式提交、交卷 | 范围版本不覆盖历史，草稿不评分，未答题不默认为错误 |
| 两个流程 / 标签页同时复习同一卡 | 复用活动会话或返回卡片版本冲突，不重复推进间隔 |
| 次日换名称复述同一目标 | 确认后复用稳定知识点和卡片，排期不重置 |

第一条免费集成验证可用 `fauxProvider` 脚本化两个写工具调用，配合内存版本仓储检查顺序与冲突；随后用数据库集成测试验证真实事务，再用假时间跑通“复述 → 测验 → 次日复习 → 刷新恢复”。不得把纯内存验证当成数据库并发已经通过。

### 18.2 首批评估样例

建议建立 20–50 个经人工检查的小样例，包括：

- 准确复述与不同表达的正确回答。
- 复述很少但不能据此判定不会。
- 笔记与复述冲突，或笔记本身错误。
- 部分正确、关键条件遗漏与真实误解。
- 点击自称掌握但独立测验失败。
- 提示后答对与延迟后独立答对。
- 超出课程范围的题目。
- 不合法引用、模型输出中断、评分无法确定。

保留人工参考依据、输出、问题类型和修改记录。模型结果一致并不等于正确，需要事实与评分标准的独立检查。

### 18.3 上线检查

- [ ] 无前端密钥，无真实用户原文进入公开日志。
- [ ] 所有用户资源与 SSE 均验证归属。
- [ ] 学习者 DTO 与内部答案 / 评分对象分离。
- [ ] 草稿、会话、作答和排期可以恢复。
- [ ] 显式 Provider / 模型与凭据来源符合配置，无意外厂商回退或个人配置继承。
- [ ] 重试、取消、预算、后台重启和旧执行器迟到结果阻断已验证。
- [ ] 首期仅 TXT / Markdown，上传白名单、资源限制及安全渲染生效。
- [ ] 到期计算与时区有回归测试。
- [ ] 空 / 加载 / 错误和小屏状态可用。
- [ ] 数据导出、删除及备份恢复有明确路径。
- [ ] 模型费用、失败率和错误告警可观察。
- [ ] 未实现功能不冒充已可用，设计示意数据不进入生产。
- [ ] 已告知 AI 评价可能出错，提供纠正入口。

### 19.3 第一版完成定义

本人能够在受保护的网页中复述所学，粘贴或上传 TXT / Markdown，确认学习范围并完成有依据的追问和考核，也能明确无测验结束。系统使用显式配置的 Pi Provider，留下版本化证据；之后复用同一知识点与回忆目标，按真实到期计划再次独立回忆，每次有效复习只更新一次排期。
